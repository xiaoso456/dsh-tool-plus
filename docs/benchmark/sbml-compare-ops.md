# SWE-bench Multilingual · 四种 harness 运行指标对比

> 说明：本文由 AI 基于运行数据整理分析，仅供参考。

对比 **DSH 标准模式（基线）**、**基线 + dsh-ops 插件**、**基线 + dsh-tool-plus 插件**、
**基线 + dsh-tool-plus 插件（不拦截 grep）** 四种 harness。
四组跑同一批题、同一模型、同一驱动器，**唯一变量是 harness**。

## 实验条件

| 项 | 值 |
|---|---|
| 数据集 | SWE-bench Multilingual，首批 20 题抽样（Rust / Java / Go / TS 各 5，含 6 条 feature 题） |
| harness | DSH 0.2.0-rc.2 + Node v22.20.0 |
| 插件版本 | dsh-ops **0.3.1**；dsh-tool-plus **0.1.13** |
| 模型 | `deepseek-v4.1-flash`（Ollama Cloud） |
| 思考强度 | `reasoningEffort: high` |
| 上下文窗口 / 最大输出 | 1,048,576 / 384,000 |
| 并发 | 2 |
| 轮次 | 每组 3 轮，每轮 20 题，合计 60 次运行 |

四个 harness 的工具面：

| 组 | 工具数 | 构成 |
|---|---|---|
| 基线 | 24 | 官方工具，未裁 |
| dsh-ops 插件组 | 35 | dsh-ops 0.3.1。24 官方 − `bash` + 11 个 `ops_*`（官方 `bash` 被 `shellPolicy: deny-host-shell` restrict 掉，由 `ops_bash` 顶替） |
| dsh-tool-plus 插件组 | 24 | dsh-tool-plus 0.1.13。**工具名与基线相同**（`bash`/`read`/`write`/`edit`/`grep`/`glob` 由插件实现）。差异有两点：① `read_image` 被移除，其读图能力并入 `read`（描述从「Read a UTF-8 text file」扩成「Read files, directories, archives, SQLite, images, documents, internal resources, and web URLs」）；② 新增 `ast_edit`（基于 ast-grep 的结构化改写），这是**额外能力**，不是顶替任何官方工具 |
| dsh-tool-plus 插件组（不拦截 grep） | 24 | dsh-tool-plus 0.1.13，同一模板。唯一区别是把插件的 `interceptorEnabled` 关掉（当时默认 `true`，会拦截 `cat`/`grep`/`find`/`sed -i`/`echo` 重定向/`nohup`/dev-server，命中即 `Blocked: …` 退回给模型），该组用于隔离「命令拦截」这一项的影响 |

指标口径：
- 步数 = 实际请求次数；工具调用 = `tool/call` 事件数，时长为 `tool/call` → 对应 `tool/result` 的墙钟。
- `totalTokens` 是**每步上下文量**不是累计值，总量按 input + cacheRead + output 求和。
- token 数全部为精确值：上游 usage 给出 input / cacheRead / output，其余文本段按 DeepSeek 官方分词器切分。

## 一、结论

| | 基线 | dsh-ops 插件组 | dsh-tool-plus 插件组 | dsh-tool-plus 插件组（不拦截 grep） |
|---|---|---|---|---|
| 分数 | **50 / 60 = 83.3%** | **50 / 60 = 83.3%** | **50 / 60 = 83.3%** | **49 / 60 = 81.7%** |
| 逐轮 | 85% / 80% / 85% | 80% / 85% / 85% | 85% / 80% / 85% | 85% / 80% / 80% |
| 墙钟 / 题 | 123 s | 117 s | 135 s | 151 s |
| token / 题 | 729,434 | 1,097,483 | 954,100 | 779,799 |

**三个插件的分数与基线持平（放开 grep 那一组低 1 题），差异全在运行成本上，而且机制各不相同：**

| 指标 | 基线 | ops 插件组 | tool-plus 插件组 | tool-plus 插件组（不拦截 grep） |
|---|---|---|---|---|
| 步数 / 题 | 24.4 | 26.3（+7.9%） | **29.7（+21.7%）** | **25.3（+3.8%）** |
| 每步回吐 token | 1,215 | 1,601（**+31.8%**） | 1,111（**−8.6%**） | 1,181（−2.8%） |
| 除系统提示词外 token / 题 | 616,169 | 901,266（+46.3%） | 766,841（+24.5%） | **620,177（+0.7%）** |
| 结束上下文均值 | 42,817 | 59,803（+39.7%） | 48,645（+13.6%） | 44,781（+4.6%） |
| 单步系统开销 | 4,642 | 7,456（+60.6%） | 6,305（+35.8%） | 6,305（+35.8%） |

- **ops 插件组：每步更肥 + 步数略增。** 它的 `ops_*` 工具回吐量比官方工具大（见第四节），每步上下文被推高，
  而每步内容又会被后续所有步重读，于是「只多走 7.9% 的步」放大成「多烧 46.3%」。
- **tool-plus 插件组：每步更省 + 步数大增。** 它的工具回吐比官方还精简（`bash` 类 790 → 343 tok/次），
  但模型多走了 21.7% 的步。成本增长几乎全部来自步数，来自线性项而非平方项。
- **tool-plus 插件组（不拦截 grep）：两种效应几乎抵消。** 放开 grep 后步数从 +21.7% 回落到 +3.8%，
  每步回吐从 −8.6% 变成 −2.8%，**除系统提示词外 token 只剩 +0.7%——四组里最接近基线的一组**。

**放开 grep 这一项，把 tool-plus 的成本增长几乎全部消掉了。** 这直接指向结论：
tool-plus 原本多出来的 21.7% 步数，主要是 grep 被拦截后模型改用 `read` 碎读导致的
（`read` 调用 459 次 vs 基线 225 次，放开后回落到 198 次，见第四节）。

**失败集合也高度一致**：四组共同全败的是 `apache__lucene-12196`、`apache__lucene-11760`、`axios__axios-4738`；
偶发失败各不相同——ops 插件组输 `apache__druid-13704` 一次，tool-plus 插件组输 `caddyserver__caddy-5404` 一次，
不拦截 grep 那一组输 `astral-sh__ruff-15543` 与 `nushell__nushell-13831` 各一次（均只挂一轮）。

## 二、token 与「除系统提示词外的 token」

**本节的口径**：系统提示词与工具定义每步重发一次，故「单步开销 × 步数」就是它在这一轮被重复计费的总额，
即下表的「系统提示词 token 合计」；「除系统提示词外的 token」= 总 token − 这个数，是把每步重发的部分剥掉后的净消耗。
四组的单步开销分别是 **基线 4,642**（提示词 530 + 工具定义 4,112）、**ops 插件组 7,456**（1,243 + 6,213）、

**结论一：ops 插件组剥掉系统提示词后仍贵 46.3%，tool-plus 插件组贵 24.5%，而不拦截 grep 那一组只贵 0.7%。**
系统提示词变胖解释不了主要差异（ops 只占总差值的 22.5%），真正的原因在每步内容与步数的组合方式。

**结论二：每步新增的内容会被后续所有步重读，所以步数的作用被放大。**
把每步新增的内容（工具回吐 + 模型生成）算出来：

| | 工具回吐 | 模型生成 | 每步新增合计 | 步数 | 除系统提示词外 token |
|---|---|---|---|---|---|
| 基线 | 1,778,076 | 355,976 | 1,458 / 步 | 1,464 | 36,970,131 |
| ops 插件组 | 2,527,219 | 432,426 | 1,874 / 步（+28.6%） | 1,579（+7.9%） | 54,075,955（+46.3%） |
| tool-plus 插件组 | 1,979,032 | 377,445 | 1,322 / 步（−9.3%） | **1,782（+21.7%）** | 46,010,471（+24.5%） |
| tool-plus 插件组（不拦截 grep） | 1,794,115 | 353,323 | 1,414 / 步（−3.0%） | 1,519（+3.8%） | 37,210,644（+0.7%） |

ops 插件组每步只多 28.6%、步数只多 7.9%，总量却多 46.3%——因为新增内容每一步都被重读（cacheRead 占总量 93%），
**总 token 大致随「每步新增内容 × 步数²」增长**，每步内容是平方项、步数是线性项。
tool-plus 插件组反过来：每步内容少 9.3%，但步数多 21.7%，总量仍多 24.5%；
而不拦截 grep 那一组两项都只小幅偏离基线，于是总量几乎持平（+0.7%）。

**推论：降本方向取决于插件属于哪种机制。**
- ops 这一类「工具更肥」的，要裁**每步回吐量**（平方项），裁步数收效甚微。
- tool-plus 这一类「工具更省但步数更多」的，要查**它为什么让模型多走步**；
  不拦截 grep 那一组证明，步数增长的主因是 grep 被拦截后的替代行为，而非工具本身更慢。

## 三、结束时上下文长度

「结束」= 模型最后一步请求时看到的总长度（`inputTokens + cacheReadTokens`），
即这道题跑完时上下文被撑到多大；「全程峰值」= 会话内任一步的最大上下文。

「减系统提示词后」= 上面的值再减去该组的单步系统提示词 token 合计（基线 4,642、ops 插件组 7,456、
tool-plus 两组均 6,305）。系统提示词每步重发、且四组厚度不同，不减掉就无法判断上下文膨胀
是插件造成的还是工具变肥造成的。

| 组 | 题次 | 结束均值 | 结束中位 | 结束峰值 | 减系统提示词后均值 | 减系统提示词后中位 | 减系统提示词后峰值 |
|---|---|---|---|---|---|---|---|
| 基线 | 60 | 42,817 | 39,550 | 100,902 | 38,175 | 34,908 | 96,260 |
| ops 插件组 | 60 | 59,803 | 52,559 | 132,993 | 52,347 | 45,103 | 125,537 |
| tool-plus 插件组 | 60 | 48,645 | 45,336 | 120,821 | 42,340 | 39,031 | 114,516 |
| tool-plus 插件组（不拦截 grep） | 60 | 44,781 | 40,151 | 97,160 | 38,476 | 33,846 | 90,855 |

差值：

| 指标 | ops 插件组 vs 基线 | tool-plus 插件组 vs 基线 | tool-plus 插件组（不拦截 grep）vs 基线 |
|---|---|---|---|
| 结束均值 | **+39.7%** | **+13.6%** | **+4.6%** |
| 结束均值（减系统提示词后） | +37.1% | +10.9% | **+0.8%** |
| 结束中位 | +32.9% | +14.6% | +1.5% |
| 结束中位（减系统提示词后） | +29.2% | +11.8% | −3.0% |
| 结束峰值 | +31.8% | +19.7% | −3.7% |
| 结束峰值（减系统提示词后） | +30.4% | +19.0% | −5.6% |

1. **减掉系统提示词后，ops 与 tool-plus 两组仍显著膨胀（+37.1% / +10.9%），
   但不拦截 grep 那一组只剩 +0.8%（峰值甚至低于基线）。**
   说明上下文变长**不是**系统提示词变厚造成的，而是每步多塞的内容累积的结果。
2. **四组的峰值都只占到 1,048,576 窗口的 9.6% / 12.7% / 11.5% / 9.3%**（减后为 9.2% / 12.0% / 10.9% / 8.7%），
   百万窗口对这 20 题完全够用，不存在截断风险。当前瓶颈不是窗口大小，而是每步重复读取带来的费用。
3. **结束长度与步数不成比例**：tool-plus 步数 +21.7% 而结束长度只 +13.6%，
   说明它每步留下的内容确实更少；ops 步数只 +7.9% 而结束长度 +39.7%，说明它每步留下的内容显著更多。
   这与第二节的每步回吐（tool-plus −8.6%、ops +31.8%）方向一致。
4. **结束均值 ≈ 结束中位**（四组分别 42,817/39,550、59,803/52,559、48,645/45,336、44,781/40,151），
   分布没有被个别长题拉歪，中位题能代表整体。

### 4.1 时间几乎全花在 shell 上

合并后的 bash 类占基线墙钟的 55.7%、ops 插件组的 52.4%、tool-plus 插件组的 34.2%、不拦截 grep 组的 30.2%。
优化墙钟的着力点始终只有一个——编译与测试命令。

### 4.2 tool-plus 的 `bash` 又快又省，但 `read` 用得又多又碎

- `bash` 类：**2,391 ms（比官方快 24%）、343 tok/次（比官方省 57%）**，峰值从 300 s 降到 60 s。
  工具本身的设计目标达到了。
- 但 `read` 被调用 **459 次**（基线 225 次，2 倍），每次只回吐 **807 tok**（基线 1,391）。
  等于用更多次、更碎的读取替代一次大读取。
- `grep` 类更极端：**310 次 vs 基线 39 次（近 8 倍）**，每次 1,024 tok。

### 4.3 放开 grep 后，碎读行为消失

同一插件、同一批题，只放开 grep 拦截：

| 工具类别 | tool-plus 插件组 | 不拦截 grep | 基线 |
|---|---|---|---|
| `read` 次数 | **459** | **198** | 225 |
| `grep` 类次数 | **310** | **46** | 39 |
| `bash` 类次数 | 1,159 | 1,337 | 1,314 |
| 步数 / 题 | 29.7（+21.7%） | 25.3（+3.8%） | 24.4 |
| 除系统提示词外 token / 题 | 766,841（+24.5%） | 620,177（+0.7%） | 616,169 |

`read` 从 459 次回落到 198 次（低于基线的 225），`grep` 类从 310 次回落到 46 次（接近基线的 39），
步数增幅从 +21.7% 收缩到 +3.8%，**除系统提示词外 token 从 +24.5% 收缩到 +0.7%**。

这基本锁定结论：**tool-plus 多出来的步数与成本，主要不是工具慢，而是 grep 被拦截后模型改用 `read` 碎读。**
放开 grep，替代行为消失，工具「更快更省」的优点才体现出来。

### 4.4 ops 的回吐膨胀来自少数几个工具

`ops_inspect_local_file` 平均一次回吐 **3,844 token**（`read` 的 2.8 倍），`web_fetch` 3,798。
合并后看，ops 的文本类比官方对应工具回吐更多：`edit` 类 133 vs 24（5.5 倍）、
`grep` 类 961 vs 482（2.0 倍）、`glob` 类 465 vs 150（3.1 倍）、`read` 1,705 vs 1,391（1.2 倍）。
未合并的单项同样明显：`ops_edit_file` 240 vs `edit` 24（10 倍）、`ops_grep` 1,007 vs `grep` 482（2.1 倍）、
`ops_glob` 640 vs `glob` 150（4.3 倍）。

### 4.5 `ast_edit` 从未被调用

tool-plus 插件组新增了 `ast_edit`（基于 ast-grep 的结构化改写，描述 1,085 字符），
但三轮 60 次运行里**一次都没用过**。它是额外能力，不顶替任何官方工具；
其定义 token 每一步都在被计费，属纯开销。

### 4.6 `job_*` 轮询是两个 tool-plus 组共同的等待来源

`job_*` 三类在不拦截 grep 组被调用 **36 次、平均 53.9 s、峰值 351 s**，比 tool-plus 插件组的 53 次 / 38.9 s 更极端，
也远高于基线的 19 次 / 8.1 s。这是纯粹的等待：命令超过 120 s 被转后台后，模型反复轮询。
它解释了为什么 tool-plus 的 `bash` 更快（2,045 ms vs 官方 3,140 ms）而整轮墙钟反而更高（151 s vs 123 s）。
